# Requirements Document

## Introduction

VeilPay is a privacy-first crypto payment application built on a four-layer privacy stack: ZK circuits (Layer 2), EVM smart contracts (Layer 1), a gas-sponsoring relayer backend (Layer 3), and a React Native mobile app (Layer 4). The scaffolding for all four layers exists but critical pieces are missing or broken, making the end-to-end privacy payment flow non-functional. This feature completes the full privacy stack so that users can make shielded deposits, generate valid ZK membership proofs, withdraw via a relayer, and scan for incoming stealth payments — all without leaking on-chain identity.

The work spans four areas:
1. **ZK Circuit** — add Merkle membership proof to `withdraw.circom` and align public inputs with the contract.
2. **Smart Contracts** — add an incremental Merkle tree to `VeilPool.sol`, fix public input alignment, generate a real `Groth16Verifier.sol`, wire `StealthAnnouncer.announce()`, and deploy to Sepolia.
3. **Relayer** — fix `relayerController.ts` to call `VeilPool.withdraw()`, add a contract allowlist, and configure secrets.
4. **Mobile App** — port `StealthAddressEngine`, add a stealth scanning loop, persist commitment/nullifier tuples, wire the real relayer and circuit artifacts, call `StealthAnnouncer.announce()` after stealth sends, and expose the `stealth` privacy level in the UI.

## Glossary

- **VeilPool**: The Solidity privacy pool contract (`packages/contracts-evm/src/VeilPool.sol`) that accepts shielded deposits and processes ZK-proven withdrawals.
- **StealthAnnouncer**: The ERC-5564 Solidity contract (`packages/contracts-evm/src/StealthAnnouncer.sol`) that emits `Announcement` events so recipients can discover incoming stealth payments.
- **Groth16Verifier**: The Solidity verifier contract auto-generated by snarkjs from the compiled circuit's `.zkey` file. Currently a stub that always returns `false`.
- **WithdrawCircuit**: The Circom 2.0 circuit (`packages/circuits/withdraw.circom`) that proves knowledge of a commitment's preimage and Merkle membership.
- **MerkleTree**: An incremental binary Merkle tree (depth 30) whose leaves are commitment hashes. The tree root is a public input to the WithdrawCircuit.
- **Commitment**: A Poseidon hash `Poseidon(nullifier, secret)` inserted as a leaf into the MerkleTree on deposit.
- **NullifierHash**: A Poseidon hash `Poseidon(nullifier)` revealed on withdrawal to prevent double-spending.
- **MerkleRoot**: The root of the MerkleTree at the time a withdrawal proof is generated; included as a public input to prevent proof replay across tree states.
- **CommitmentRecord**: A tuple `{nullifier, secret, commitmentHash, leafIndex, merkleRoot, amount, token, chainKey, timestamp}` persisted in device SecureStore after a deposit.
- **Relayer**: The Express backend service (`apps/backend/`) that sponsors gas for `VeilPool.withdraw()` calls, breaking the link between depositor and withdrawer.
- **StealthAddressEngine**: The secp256k1 ECDH engine (`apps/indexer/src/stealth/crypto.ts`) that generates and checks stealth addresses. Must be ported to the mobile app.
- **ViewingKey**: The user's secp256k1 private key used to check whether an `Announcement` event belongs to them.
- **ZkpProver**: The headless WebView component (`apps/consumer-app/src/components/ZkpProver.tsx`) that runs snarkjs inside a WebView to generate Groth16 proofs off the main JS thread.
- **PrivacyLevel**: An enum value (`'standard' | 'stealth' | 'max'`) stored in `settingsStore` that controls which privacy mechanism is used for a payment.
- **snarkjs**: The JavaScript library used to generate and verify Groth16 proofs in-browser and in WebView environments.
- **circomlib**: The standard Circom circuit library providing `Poseidon` and `MerkleTreeChecker` templates.
- **ERC-5564**: The Ethereum standard for stealth address announcements implemented by `StealthAnnouncer`.
- **SecureStore**: The Expo SecureStore API used for encrypted on-device persistence of sensitive data such as `CommitmentRecord` tuples.

## Requirements

### Requirement 1: Merkle Tree Integration in the ZK Circuit

**User Story:** As a privacy pool user, I want my withdrawal proof to demonstrate that my commitment exists in the pool's Merkle tree, so that the contract can verify membership without revealing which leaf is mine.

#### Acceptance Criteria

1. WHEN `withdraw.circom` is compiled, THE WithdrawCircuit SHALL include a `MerkleTreeChecker` component from circomlib that verifies a Merkle membership proof of depth 20.
2. THE WithdrawCircuit SHALL accept the following private inputs: `nullifier`, `secret`, `pathElements[20]`, and `pathIndices[20]`.
3. THE WithdrawCircuit SHALL accept the following public inputs: `merkleRoot`, `nullifierHash`, `recipient`, and `amount`.
4. WHEN the circuit is evaluated, THE WithdrawCircuit SHALL constrain that `Poseidon(nullifier, secret)` equals the `leaf` input signal of `MerkleTreeChecker`.
5. WHEN the circuit is evaluated, THE WithdrawCircuit SHALL constrain that `Poseidon(nullifier)` equals `nullifierHash`.
6. WHEN the circuit is evaluated with a `pathElements`/`pathIndices` path that does not resolve to `merkleRoot`, THE WithdrawCircuit constraint system SHALL be unsatisfiable (no valid witness exists).
7. THE WithdrawCircuit constraint system SHALL be satisfiable if and only if `pathElements` and `pathIndices` form a valid Merkle path from `Poseidon(nullifier, secret)` to `merkleRoot`.
8. IF `withdraw.circom` is compiled with a `pathElements`/`pathIndices` path that does not correspond to any leaf in the tree, THEN no valid proof SHALL be producible for that input.
9. WHEN `compile.sh` is executed successfully, THE WithdrawCircuit SHALL produce `build/withdraw.wasm`, `withdraw_final.zkey`, `verification_key.json`, and an updated `Groth16Verifier.sol` as outputs.
10. IF `compile.sh` fails at any step (compilation, ceremony, or export), THEN the script SHALL exit with a non-zero code and print the failing step to stderr without overwriting any previously valid artifacts.
11. WHEN a `CommitmentRecord` is stored after deposit, iteratively hashing each `pathElements[i]` with the sibling at `pathIndices[i]` from the leaf up to the root SHALL produce the same `merkleRoot` stored in the record.

### Requirement 2: Incremental Merkle Tree in VeilPool

**User Story:** As a smart contract auditor, I want `VeilPool` to maintain a cryptographically sound Merkle tree of commitments, so that withdrawal proofs can be verified against a known root.

#### Acceptance Criteria

1. THE VeilPool SHALL maintain an incremental binary Merkle tree of depth 20 whose leaves are commitment hashes inserted in deposit order.
2. WHEN a deposit is accepted, THE VeilPool SHALL insert the commitment hash as the next leaf in the MerkleTree and update the stored `merkleRoot`.
3. THE VeilPool SHALL store the 30 most recent Merkle roots produced by successful deposit insertions to allow proof generation against slightly stale roots without requiring atomic proof-and-withdraw.
4. WHEN `VeilPool.withdraw()` is called, THE VeilPool SHALL verify that the supplied `merkleRoot` is one of the 30 stored valid roots and SHALL revert with `InvalidMerkleRoot` if it is not.
5. WHEN `VeilPool.withdraw()` is called, THE VeilPool SHALL pass `(merkleRoot, nullifierHash, recipient, amount)` as the four public inputs to `Groth16Verifier.verifyProof()`.
6. IF `Groth16Verifier.verifyProof()` returns `false`, THEN THE VeilPool SHALL revert with `InvalidProof`.
7. IF `nullifierHash` has already been spent, THEN THE VeilPool SHALL revert with `NullifierAlreadySpent`.
8. WHEN a withdrawal succeeds, THE VeilPool SHALL mark `nullifierHash` as spent and emit a `Withdrawal` event containing `nullifierHash`, `recipient`, `token`, and `amount`.
9. WHEN a valid withdrawal proof is submitted, THE VeilPool SHALL transfer exactly `amount` minus `(amount * WITHDRAW_FEE_BPS / 10000)` to `recipient` and the fee to `feeRecipient`.
10. WHEN `nullifierHash` is submitted for a second time, THE VeilPool SHALL revert with `NullifierAlreadySpent` regardless of proof validity.
11. WHEN the Merkle tree has reached its maximum leaf capacity (2^20 leaves), THE VeilPool SHALL revert any new deposit with `TreeFull`.

### Requirement 3: Real Groth16Verifier Generation

**User Story:** As a developer, I want a real `Groth16Verifier.sol` generated from the compiled circuit, so that on-chain proof verification actually works instead of always returning `false`.

#### Acceptance Criteria

1. WHEN `compile.sh` is executed to completion, THE Groth16Verifier SHALL be overwritten with a contract generated by `snarkjs zkey export solidityverifier`.
2. THE Groth16Verifier SHALL implement `verifyProof(bytes calldata proof, bytes32[] calldata publicInputs) external view returns (bool)` where `proof` is the ABI-encoded Groth16 proof structure output by snarkjs and `publicInputs` are the circuit's public signals in circuit-declared order (`merkleRoot`, `nullifierHash`, `recipient`, `amount`).
3. WHEN a proof generated by `snarkjs.groth16.fullProve()` using `withdraw.wasm` and `withdraw_final.zkey` is supplied with its matching public inputs in circuit-declared order, THE Groth16Verifier SHALL return `true` without reverting.
4. WHEN a malformed `proof` bytes value, a cryptographically incorrect proof, or a `publicInputs` array with the wrong element count is supplied, THE Groth16Verifier SHALL return `false` without reverting.
5. WHEN a proof generated by `snarkjs.groth16.fullProve()` using a different circuit's zkey is supplied, THE Groth16Verifier SHALL return `false`.
6. WHEN `compile.sh` completes and the resulting `Groth16Verifier.sol` is deployed, a proof generated by `ZkpProver` in the mobile app SHALL be accepted by the deployed verifier (end-to-end round-trip: prove in app → verify on chain).

### Requirement 4: StealthAnnouncer Integration in Deposit and Send Flows

**User Story:** As a stealth payment recipient, I want the sender's app to call `StealthAnnouncer.announce()` after every stealth send, so that I can discover incoming payments by scanning announcement events.

#### Acceptance Criteria

1. WHEN `privacyLevel === 'stealth'` and a stealth payment is sent via `usePaymentTransaction`, THE Mobile_App SHALL call `StealthAnnouncer.announce()` with `schemeId = 1`, the derived `stealthAddress`, the sender's `ephemeralPublicKey`, and zero-length bytes as `metadata`.
2. IF `ephemeralPublicKey` is empty or `stealthAddress` is the zero address (`0x0000000000000000000000000000000000000000`), THEN THE Mobile_App SHALL display an error to the user, abort the `StealthAnnouncer.announce()` call, and allow the underlying send transaction to proceed.
3. WHEN `StealthAnnouncer.announce()` is called with a zero-length `ephemeralPubKey`, THE StealthAnnouncer SHALL revert with an error indicating the ephemeral key is empty.
4. WHEN `StealthAnnouncer.announce()` is called with `stealthAddress == address(0)`, THE StealthAnnouncer SHALL revert with an error indicating the stealth address is zero.
5. WHEN a valid `announce()` call is made, THE StealthAnnouncer SHALL emit an `Announcement` event containing `schemeId`, `stealthAddress`, `caller`, `ephemeralPubKey`, and `metadata`.
6. WHEN `privacyLevel === 'stealth'` and `generateStealthAddress()` succeeds and the send transaction is submitted to the network, THE Mobile_App SHALL call `StealthAnnouncer.announce()` before marking the transaction as confirmed.
7. WHILE `privacyLevel` is `'standard'` or `'max'`, THE Mobile_App SHALL NOT call `StealthAnnouncer.announce()`.
8. IF `StealthAnnouncer.announce()` reverts or the transaction fails, THEN THE Mobile_App SHALL display an error indicating the announcement failed and SHALL NOT block the user from viewing the send transaction result.

### Requirement 5: Sepolia Testnet Deployment

**User Story:** As a developer, I want all contracts deployed to Sepolia testnet with real addresses, so that the mobile app and relayer can interact with live contracts instead of zero-address placeholders.

#### Acceptance Criteria

1. WHEN the deployment script is executed against Sepolia, THE Deployment_Script SHALL deploy contracts in this order: `Groth16Verifier` first, then `VeilPool` (passing the `Groth16Verifier` address), then `StealthAnnouncer`, and SHALL record all three addresses.
2. WHEN all three contracts are deployed successfully, THE Deployment_Script SHALL write their checksummed 42-character Ethereum addresses to `packages/contracts-evm/deployments/sepolia.json` in a format that requires no additional transformation to use.
3. WHEN `VeilPool` is deployed, THE Deployment_Script SHALL pass the deployed `Groth16Verifier` address as the `_verifier` constructor argument.
4. IF any contract deployment transaction reverts, times out after 60 seconds, or encounters an RPC error, THEN THE Deployment_Script SHALL exit with a non-zero code, print to stderr identifying which contract failed and why, and SHALL NOT write any addresses to the deployment configuration file.
5. THE Mobile_App SHALL read Sepolia contract addresses from `sepolia.json` and SHALL NOT use `0x0000000000000000000000000000000000000000` as a contract address anywhere in the payment or scanning flows.
6. WHEN the Mobile_App reads `sepolia.json`, IF any address entry is not a valid 42-character checksummed Ethereum address, THEN THE Mobile_App SHALL treat it as a configuration error and disable the privacy payment flow.

### Requirement 6: Relayer Backend Fix

**User Story:** As a privacy pool user, I want the relayer to call `VeilPool.withdraw()` on my behalf, so that my withdrawal transaction is gas-sponsored and my identity is not linked to the deposit.

#### Acceptance Criteria

1. WHEN `POST /api/v1/relayer/withdraw` is called with a valid proof payload, THE Relayer SHALL call `VeilPool.withdraw(nullifierHash, proof, recipient, token, amount)` on the deployed `VeilPool` contract.
2. THE Relayer SHALL NOT call `Groth16Verifier.verifyProof()` directly; proof verification SHALL occur inside `VeilPool.withdraw()`.
3. THE Relayer SHALL maintain a static allowlist of permitted `VeilPool` contract addresses loaded from environment configuration at startup.
4. IF the `contractAddress` field in the request body is absent or is not present in the allowlist, THEN THE Relayer SHALL return HTTP 400 with a JSON error body and SHALL NOT submit any transaction.
5. IF `RELAYER_PRIVATE_KEY` is not set in the environment, THEN THE Relayer SHALL return HTTP 503 with `{"error": "Relayer not configured"}` for all withdraw requests.
6. WHEN `VeilPool.withdraw()` reverts on-chain with a reason string, THE Relayer SHALL return HTTP 422 with the revert reason in the response body and SHALL NOT retry automatically; WHEN the revert contains no reason string, THE Relayer SHALL return HTTP 422 with a generic "transaction reverted" message.
7. WHEN a withdrawal transaction is successfully submitted, THE Relayer SHALL return HTTP 200 with `{"success": true, "txHash": "<hash>"}`.
8. IF any of `nullifierHash`, `proof`, `recipient`, `token`, or `amount` are absent or fail type validation (e.g., `nullifierHash` not a `bytes32` hex string, `amount` not a positive numeric string), THEN THE Relayer SHALL return HTTP 400 with a field-level validation error and SHALL NOT submit any transaction.
9. WHEN `VeilPool.withdraw()` reverts due to an invalid proof, THE Relayer SHALL return HTTP 422 and the relayer wallet balance SHALL remain unchanged (no gas consumed for the failed simulation).

### Requirement 7: Commitment and Nullifier Persistence in the Mobile App

**User Story:** As a privacy pool depositor, I want my commitment and nullifier data persisted securely on my device after a deposit, so that I can generate a valid withdrawal proof later without losing access to my funds.

#### Acceptance Criteria

1. WHEN a `VeilPool.deposit()` transaction is confirmed, THE Mobile_App SHALL persist a `CommitmentRecord` identified by `commitmentHash` and containing `{nullifier, secret, commitmentHash, leafIndex, merkleRoot, amount, token, chainKey, timestamp, spent: false}` to SecureStore.
2. THE Mobile_App SHALL use SecureStore's hardware-backed encryption to write `CommitmentRecord` entries; IF hardware-backed encryption is unavailable on the device, THE Mobile_App SHALL fall back to software-backed encryption and SHALL NOT store the record in plaintext.
3. WHEN the user initiates a withdrawal, THE Mobile_App SHALL retrieve the `CommitmentRecord` matching the requested `commitmentHash` from SecureStore and use it to construct the Merkle proof inputs for `ZkpProver`; IF no matching record is found, THE Mobile_App SHALL display an error indicating the commitment data is missing and SHALL NOT attempt to generate a proof.
4. WHEN a withdrawal is confirmed on-chain, THE Mobile_App SHALL update the corresponding `CommitmentRecord` in SecureStore by setting `spent` to `true`.
5. WHEN a `CommitmentRecord` is written to SecureStore and then read back, the deserialized values of `nullifier`, `secret`, `commitmentHash`, `leafIndex`, `merkleRoot`, `amount`, `token`, `chainKey`, `timestamp`, and `spent` SHALL each equal their originally written values.
6. THE Mobile_App SHALL NOT write `nullifier` or `secret` values to `transactionStore`, `AsyncStorage`, or any storage mechanism that does not use SecureStore encryption.
7. IF the SecureStore write operation fails after a deposit is confirmed on-chain, THEN THE Mobile_App SHALL display a persistent error warning the user that their commitment data was not saved and that funds may be at risk, and SHALL retry the write on the next app launch.

### Requirement 8: Real Relayer Integration in the Mobile App

**User Story:** As a privacy pool user, I want the mobile app to submit my ZK proof to the real relayer backend, so that my withdrawal is actually executed on-chain instead of returning a mock transaction hash.

#### Acceptance Criteria

1. WHEN `privacyLevel === 'max'` and a proof is generated, THE Mobile_App SHALL call the real relayer endpoint at the URL configured in `RELAYER_BASE_URL` (not a mock `setTimeout`).
2. THE Mobile_App SHALL send a JSON body containing `{nullifierHash, proof, publicSignals, recipient, token, amount, chainKey}` to `POST /api/v1/relayer/withdraw`.
3. IF the relayer returns a non-2xx HTTP response, THEN THE Mobile_App SHALL display the HTTP error message to the user and set `txStatus` to `'failed'`.
4. WHEN the relayer returns `{"success": true, "txHash": "<hash>"}`, THE Mobile_App SHALL use the returned `txHash` to poll for on-chain confirmation via `pollTransactionStatus`.
5. THE Mobile_App SHALL apply a 30-second timeout to the relayer HTTP request; IF the request times out before an HTTP response is received, THEN THE Mobile_App SHALL display a timeout error and set `txStatus` to `'failed'`; IF an HTTP response is received before the timeout, THE Mobile_App SHALL use the HTTP response status and SHALL NOT display a timeout error.

### Requirement 9: Real Circuit Artifacts in ZkpProver

**User Story:** As a privacy pool user, I want the ZkpProver to load real WASM and zkey files, so that proof generation actually works instead of failing with a 404 from a non-existent CDN URL.

#### Acceptance Criteria

1. THE ZkpProver SHALL load `withdraw.wasm` and `withdraw_final.zkey` from URLs configured in a constants file (e.g., `CIRCUIT_WASM_URL` and `CIRCUIT_ZKEY_URL`) rather than hardcoded `api.veilpay.io` paths.
2. WHEN the configured WASM or zkey URL returns a non-200 response, THE ZkpProver SHALL post a `PROOF_ERROR` message to React Native with a descriptive error string.
3. THE ZkpProver SHALL pass `{nullifier, secret, pathElements, pathIndices, merkleRoot, nullifierHash, recipient, amount}` as the full input object to `snarkjs.groth16.fullProve()`.
4. WHEN `snarkjs.groth16.fullProve()` succeeds, THE ZkpProver SHALL post a `PROOF_SUCCESS` message containing `{proof, publicSignals}` to React Native.
5. WHEN `snarkjs.groth16.fullProve()` throws, THE ZkpProver SHALL post a `PROOF_ERROR` message containing the error string to React Native.
6. FOR ALL valid `CommitmentRecord` inputs, the proof generated by `ZkpProver` SHALL be accepted by `Groth16Verifier.verifyProof()` on-chain (end-to-end round-trip: prove in app → verify on chain).

### Requirement 10: Stealth Address Engine Port to Mobile App

**User Story:** As a stealth payment recipient, I want the mobile app to include the full `StealthAddressEngine` from the indexer, so that I can check whether incoming announcements belong to me using my viewing key.

#### Acceptance Criteria

1. THE Mobile_App SHALL include a `StealthAddressEngine` module at `apps/consumer-app/src/utils/stealthEngine.ts` that is a direct port of `apps/indexer/src/stealth/crypto.ts`.
2. THE StealthAddressEngine SHALL expose `generateStealthKeyPair()`, `deriveStealthAddress()`, `recoverStealthPrivateKey()`, and `checkStealthAddressMatch()` with identical signatures to the indexer version.
3. WHEN `checkStealthAddressMatch(stealthAddress, ephemeralPublicKey, viewingPrivateKey)` is called with a matching announcement, THE StealthAddressEngine SHALL return `true`.
4. WHEN `checkStealthAddressMatch(stealthAddress, ephemeralPublicKey, viewingPrivateKey)` is called with a non-matching announcement, THE StealthAddressEngine SHALL return `false`.
5. FOR ALL `(ephemeralPrivateKey, viewingPublicKey)` pairs, `deriveStealthAddress()` followed by `checkStealthAddressMatch()` with the corresponding `viewingPrivateKey` SHALL return `true` (round-trip property).
6. FOR ALL randomly generated `(ephemeralPrivateKey, viewingPublicKey)` pairs, the derived `stealthAddress` SHALL be a valid EVM address (40 hex characters with `0x` prefix).

### Requirement 11: Stealth Scanning Loop in the Mobile App

**User Story:** As a stealth payment recipient, I want the mobile app to periodically scan `StealthAnnouncer` events and check each announcement against my viewing key, so that I am notified when I receive a stealth payment.

#### Acceptance Criteria

1. THE Mobile_App SHALL include a `useStealthScanner` hook that polls `StealthAnnouncer` for `Announcement` events on a configurable interval (default: 60 seconds).
2. WHEN the scanning loop runs, THE useStealthScanner SHALL fetch all `Announcement` events emitted since the last scanned block and check each one using `StealthAddressEngine.checkStealthAddressMatch()` with the user's `viewingPrivateKey`.
3. WHEN `checkStealthAddressMatch()` returns `true` for an announcement, THE useStealthScanner SHALL add the stealth payment to the user's transaction history with status `'incoming_stealth'`.
4. THE useStealthScanner SHALL persist the last scanned block number to SecureStore so that rescanning from block 0 is not required on every app launch.
5. WHEN the app is in the background, THE useStealthScanner SHALL pause polling and resume when the app returns to the foreground.
6. IF the RPC call to fetch `Announcement` events fails, THEN THE useStealthScanner SHALL log the error and retry on the next scheduled interval without crashing.
7. FOR ALL `Announcement` events emitted by `StealthAnnouncer` for the user's viewing key, THE useStealthScanner SHALL detect every matching announcement within two polling intervals (completeness property).

### Requirement 12: Stealth Privacy Level Exposed in UI

**User Story:** As a user, I want to select "Stealth" as a privacy level in the payment flow, so that I can send payments to one-time stealth addresses without the option being hidden or unreachable.

#### Acceptance Criteria

1. THE SettingsStore SHALL define `PrivacyLevel` as `'standard' | 'stealth' | 'max'` (adding `'stealth'` to the existing union type).
2. THE PrivacyLevelScreen SHALL render a selectable option for `'stealth'` privacy level alongside `'standard'` and `'max'`.
3. WHEN the user selects `'stealth'` and taps "CONFIRM & SEND", THE Mobile_App SHALL navigate to the payment confirmation screen with `privacyLevel === 'stealth'`.
4. WHEN `privacyLevel === 'stealth'` in `usePaymentTransaction`, THE Mobile_App SHALL execute the stealth address derivation flow (ECDH via `StealthAddressEngine.deriveStealthAddress()`) and call `StealthAnnouncer.announce()` after the transaction is confirmed.
5. WHILE `privacyLevel` is `'standard'` or `'max'`, THE Mobile_App SHALL NOT call `StealthAnnouncer.announce()`.
6. THE PrivacyLevelScreen SHALL display a description for the `'stealth'` option that accurately describes one-time stealth address behavior.
7. WHEN `defaultPrivacyLevel` is set to `'stealth'` in `settingsStore`, THE PrivacyLevelScreen SHALL pre-select the `'stealth'` option on load.

### Requirement 13: Contract Address Constants in the Mobile App

**User Story:** As a developer, I want the mobile app to reference deployed Sepolia contract addresses from a single constants file, so that there are no zero-address placeholders anywhere in the app code.

#### Acceptance Criteria

1. THE Mobile_App SHALL define contract address constants in `apps/consumer-app/src/constants/contracts.ts` for `VEIL_POOL_ADDRESS`, `STEALTH_ANNOUNCER_ADDRESS`, and `GROTH16_VERIFIER_ADDRESS` on Sepolia.
2. THE Mobile_App SHALL read contract addresses exclusively from `contracts.ts` and SHALL NOT hardcode zero addresses (`0x0000...`) anywhere in the payment or scanning flows.
3. IF a contract address constant is set to the zero address, THEN THE Mobile_App SHALL display a configuration error on startup and SHALL disable the privacy payment flow.
4. WHEN the active network is not Sepolia, THE Mobile_App SHALL display a "Privacy pool not available on this network" message and SHALL disable the `'max'` and `'stealth'` privacy levels.
