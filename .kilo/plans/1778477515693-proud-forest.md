# Security Audit & Code Review Plan

**Objective:** Perform a comprehensive security audit and code review to identify vulnerabilities, logical loopholes, and architectural weaknesses, ensuring the system is production-ready for both mainnet and testnet environments.

## Phase 1: Reconnaissance & Architecture Mapping

### 1.1 System Architecture Survey
**Goal:** Understand the complete system architecture, data flows, and trust boundaries.

- **Backend API (`apps/backend`)**: Express.js API with Prisma ORM, PostgreSQL, Redis/BullMQ
- **Consumer App (`apps/consumer-app`)**: React Native (Expo) mobile wallet
- **Smart Contracts:**
  - EVM: Solidity contracts (`packages/contracts-evm`) - VeilPool, VeilRegistry, Groth16Verifier
  - Solana: Rust/Anchor (`packages/contracts-solana`) - veil_pool
  - Aptos: Move (`packages/contracts-aptos`) - veil_pool
- **Indexer:** Blockchain event indexer (`apps/indexer`)

### 1.2 Technology Stack Inventory
- TypeScript/Node.js (backend)
- React Native / Expo (mobile)
- Solidity ^0.8.25 (EVM contracts)
- Rust/Anchor (Solana)
- Move (Aptos)
- Prisma ORM + PostgreSQL
- Redis + BullMQ (webhook queues)
- Ethers.js v6 (blockchain interaction)

## Phase 2: Wallet Security & Fund Management Audit

### 2.1 Private Key Management & Seed Phrase Generation
- **BIP-39 Mnemonic Generation (`apps/consumer-app/src/utils/bip39.ts`)**
  - Audit entropy source: `expo-crypto` `getRandomBytesAsync()` (secure) vs browser `crypto.getRandomValues()` (secure)
  - Verify no `Math.random()` usage for cryptographic purposes
  - Check custom SHA-256 implementation (`sha256PureJs`) - **Critical risk:** Custom crypto primitives are dangerous
  - Validate BIP-39 compliance (12/24 word generation, checksum)
  
- **Mnemonic Storage (`apps/consumer-app/src/utils/transactions.ts`)**
  - `storeMnemonic()`: Uses `expo-secure-store` with `WHEN_UNLOCKED_THIS_DEVICE_ONLY`
  - **Critical:** No AsyncStorage fallback for mnemonic - good security practice but may cause data loss
  - Verify key derivation isolation (mnemonic never returned outside closure)
  
- **Private Key Derivation (`apps/consumer-app/src/utils/secureSigner.ts`)**
  - `signAndSendTransaction()`: Scope-local mnemonic handling - mnemonic retrieved, used, and eligible for GC
  - Verify no intermediate storage of private key material
  - Check HDNodeWallet derivation path: `m/44'/60'/0'/0/0` (standard Ethereum)

### 2.2 Fund Lifecycle Security
- **Transaction Signing & Broadcasting**
  - `secureSigner.ts`: Balance check before signing (prevents overdrafts)
  - Gas estimation with 15% buffer (`gasEstimator.ts`)
  - **Risk:** Gas price manipulation - fixed buffer may not account for extreme network congestion
  - Transaction validation: recipient address format, amount > 0
  - **Missing:** EIP-712 typed data signing for secure contract interactions

- **Transaction Replacement (`replaceTransaction` in `secureSigner.ts`)**
  - Speed-up and cancel functionality
  - **Risk:** `SPEED_UP_MULTIPLIER = 1.1` (10%) may not be sufficient during gas wars
  - **Risk:** Cancel transaction sends 0 value to self - may fail if recipient validation rejects self-transfers
  - **Missing:** Transaction replacement EIP-1559 edge case handling (same nonce, different tx)

### 2.3 Nonce Management & Replay Attack Prevention
- **Risk:** No explicit nonce management in `secureSigner.ts` - relies on provider-managed nonce
- **Risk:** No chain ID verification before signing in mobile app
- `rpcPool.ts`: `staticNetwork: true` on JsonRpcProvider - prevents network confusion but may miss chain reorgs
- **Missing:** Replay protection for cross-network transactions (testnet vs mainnet)

### 2.4 Data Exposure Risks
- **`ExportPrivateKeyScreen.tsx`:**
  - Biometric authentication before revealing private key
  - **Risk:** Clipboard copy of private key to system clipboard (accessible to other apps on Android)
  - **Risk:** `privateKey` state persists in React component memory after navigation
  - No auto-hide timeout after reveal

- **`multiChainDerivation.ts`:**
  - **Critical flaw:** Mock/deterministic address generation for Solana, Aptos, Stellar
  - Uses keccak256 hash + seed string instead of proper Ed25519/curve25519 derivation
  - Generated addresses are NOT cryptographically secure for receiving funds
  - This is marked as "demo purposes" but may still mislead users

## Phase 3: Network & Integration Readiness

### 3.1 RPC Provider Configuration
- **`rpcPool.ts`:** Weighted round-robin across Alchemy, Infura, public fallbacks
  - **Risk:** API keys embedded in frontend (`EXPO_PUBLIC_ALCHEMY_API_KEY`) - easily extracted from app bundle
  - **Risk:** Public fallback endpoints (LlamaRPC, official endpoints) have rate limits and may be unreliable
  - **Risk:** No authentication for Solana/Aptos RPC endpoints
  - Circuit breaker: 3 failures → 30s cooldown - may be too aggressive for mobile networks

### 3.2 Mainnet vs Testnet Configuration
- `walletStore.ts`: `isTestnet` flag on chains - **Risk:** UI may not clearly distinguish testnet from mainnet
- **Risk:** Testnet and mainnet mnemonic share the same derivation path - cross-contamination if users import testnet wallet to mainnet
- **Missing:** Network isolation (testnet transactions should never use mainnet RPC accidentally)

### 3.3 Network Switching & Validation
- `walletStore.ts` `setActiveChain()`: Switches chain but doesn't verify derived address for new chain
- **Risk:** User may send to an Ethereum address on Polygon without proper checksum validation
- `envValidation.ts`: Relaxed critical requirements in development mode - **Risk:** May leak to production builds

## Phase 4: Identifier & Engine Logic Audit

### 4.1 Address Derivation & Validation
- **`deriveAddressesForAllChains()` in `multiChainDerivation.ts`:**
  - **EVM:** Correct BIP-44 path `m/44'/60'/0'/0/0` - valid
  - **Solana:** Mock Base58 encoding - invalid for production. Should use proper Ed25519 key generation
  - **Aptos:** Mock hash - invalid. Should use proper BLS12-381 or Ed25519 derivation
  - **Stellar:** Mock encoding - invalid. Should use proper Ed25519 derivation
  - **Severity: Critical** - These mock addresses will not correspond to actual blockchain addresses

### 4.2 Invoice Engine Logic (`apps/backend/src/routes/invoice.ts`)
- Invoice creation: Validates merchant viewing key exists for chain
- **Risk:** Race condition between invoice creation and payment (payment address may change)
- Invoice expiry: `expiresInMinutes` converted to `Date` - timezone-safe
- **Risk:** No idempotency key on invoice creation (duplicate invoice creation possible)
- Invoice status polling: `/:id/status` is public - **Risk:** Invoice enumeration (brute force UUIDs)
- **Missing:** Invoice payment address rotation for privacy (reusing same address)

### 4.3 Webhook Engine (`apps/backend/src/jobs/webhookQueue.ts`)
- HMAC-SHA256 payload signing for merchant verification
- 3 retries with exponential backoff (5s, 30s, 120s)
- **Risk:** Webhook delivery confirmation URL may be attacker-controlled (SSRF risk)
- **Risk:** No signature verification on incoming webhooks from payment providers (Onramp, Transak)
- **Risk:** `webhookSigningSecret` hard-coded dev default in `config/index.ts` (mitigated for production)

### 4.4 Transaction Parsing & Event Listening
- **`txStatusPoller.ts`:**
  - Exponential backoff (2s → 4s → 6s → 8s)
  - 120s timeout with "pending" status preserved
  - **Risk:** No maximum retry limit on failed RPC calls
  - **Risk:** Transaction may be mined but receipt not found due to RPC inconsistency
  - AbortController cleanup - good practice

## Phase 5: Vulnerability Assessment

### 5.1 Smart Contract Vulnerabilities (EVM - `VeilPool.sol`)
- **Reentrancy:** `ReentrancyGuard` is inherited and `nonReentrant` is on deposit/withdraw - **good**
- **Pausable:** Owner can pause - good for emergency
- **Integer Overflow:** Solidity ^0.8.25 has built-in overflow checks - **safe**
- **Fee Calculation:** `(_amount * DEPOSIT_FEE_BPS) / 10000` - fine for current fee 30 bps (0.3%)
- **Front-running:** No commit-reveal scheme - deposit commitment is visible before execution
- **Missing:** `rescueETH()` sends to `feeRecipient` instead of owner (intentional?)
- **Risk:** Merkle tree not implemented (flat array of commitments) - ZK proof generation may be impossible
- **Risk:** `IVerifySignature` interface doesn't enforce view function (external call may write state)

### 5.2 Smart Contract Vulnerabilities (Solana - `veil_pool`)
- **Anchor framework:** Generally secure with proper account validation
- **Risk:** `verify_proof()` is a hardcoded `false` - contract will never allow withdrawals
- **Risk:** No check for duplicate commitments in deposit
- **Risk:** `NullifierSet` and `CommitmentSet` stored in account data - will hit account size limits
- **Risk:** No rent exemption check on pool initialization

### 5.3 Smart Contract Vulnerabilities (Aptos - `veil_pool.move`)
- **Risk:** Direct call to `borrow_global_mut<Pool<CoinType>>(@veilpay)` - assumes single pool
- **Risk:** `verify_proof()` hardcoded `false` - same as Solana
- **Risk:** No duplicate commitment check

### 5.4 Backend API Vulnerabilities
- **Authentication (`auth.ts`):**
  - HMAC-SHA256 with timestamp (5-minute window) - good
  - Timing-safe comparison - good
  - **Risk:** `apiKeyHash` is `SHA256(apiKey + salt)` - susceptible to rainbow table if salt is known
  - **Risk:** No rate limiting on auth attempts specifically
  - **Risk:** `buildSignedPayload` uses `req.rawBody` - may not be present depending on body parser

- **Rate Limiting (`rateLimiter.ts`):**
  - Per-merchant tiered limits (basic/pro/enterprise)
  - LRU cache for limiter instances (5000 entries, 5m TTL)
  - **Risk:** `globalRateLimiter` max 1000 req/min - may be too high for DDoS prevention
  - **Risk:** `invoiceStatusRateLimiter` only 30 req/min - may be too restrictive for legitimate polling

- **SQL Injection:** Prisma ORM prevents SQL injection - **safe**
- **NoSQL Injection:** Not applicable (PostgreSQL only)

### 5.5 Consumer App Vulnerabilities
- **Deep Link Injection (`deepLinking.ts`):**
  - M2 fix: Address validation before accepting from deep links
  - Amount validation: numeric only, capped at 1e9
  - **Risk:** Token symbol validation only checks alphanumeric - may allow injection of display text
  - URI validation: only accepts `wc:` prefix - good

- **Secure Storage (`secureStateStorage.ts`):**
  - SENSITIVE_STORE_NAMES pattern - prevents mnemonic leakage to AsyncStorage
  - **Risk:** If SecureStore fails, sensitive data is silently lost (no user notification)
  - **Risk:** `WHEN_UNLOCKED_THIS_DEVICE_ONLY` may cause issues on devices without secure enclave

- **RPC Pool (`rpcPool.ts`):**
  - **Risk:** API keys embedded in app bundle (Alchemy, Infura)
  - **Risk:** Override URL from environment variables without validation
  - **Risk:** `getPoolStatus` exposes internal circuit breaker state

### 5.6 Dependency Vulnerabilities
- **Risk:** `ethers@6.16.0` - check for known CVEs
- **Risk:** `react-native@0.83.6` - check for known CVEs
- **Risk:** `expo@55.0.17` - large surface area for vulnerabilities
- **Risk:** `@walletconnect/sign-client@2.23.9` - critical dependency for dApp connections

## Phase 6: Findings Categorization

### Critical Severity
| ID | Finding | Location | Impact |
|----|---------|----------|--------|
| CR-1 | Mock multi-chain address derivation generates invalid addresses for Solana, Aptos, Stellar | `multiChainDerivation.ts` | Funds sent to these addresses are permanently lost |
| CR-2 | Custom SHA-256 implementation in BIP-39 logic | `bip39.ts` | Side-channel attacks, incorrect hashes, potential for infinite loops |
| CR-3 | Private key exported to system clipboard | `ExportPrivateKeyScreen.tsx` | Clipboard accessible to other apps (Android especially) |
| CR-4 | Smart contract proof verification always returns false | All contract implementations | Privacy pool withdrawals are impossible |
| CR-5 | API keys (Alchemy, Infura) bundled in mobile app | `rpcPool.ts`, `rpc.ts` | Keys can be extracted and abused by attackers |

### High Severity
| ID | Finding | Location | Impact |
|----|---------|----------|--------|
| HI-1 | No explicit chain ID verification before signing | `secureSigner.ts` | Cross-network replay attacks |
| HI-2 | Gas buffer (15%) may be insufficient during congestion | `gasEstimator.ts` | Transactions stuck in mempool |
| HI-3 | Speed-up multiplier (1.1x) too conservative | `secureSigner.ts` | Transaction replacement failures |
| HI-4 | Webhook delivery URL not validated for SSRF | `webhookQueue.ts` | Server-Side Request Forgery |
| HI-5 | Testnet/mainnet mnemonic derivation path collision | `walletStore.ts` | Fund loss from address cross-contamination |
| HI-6 | No invoice idempotency key | `invoice.ts` | Duplicate invoice creation |

### Medium Severity
| ID | Finding | Location | Impact |
|----|---------|----------|--------|
| ME-1 | Invoice status endpoint is public (no auth) | `invoice.ts` | Invoice enumeration, privacy leakage |
| ME-2 | Rate limiter global limit too high (1000/min) | `rateLimiter.ts` | DDoS risk |
| ME-3 | `rawBody` may not be present for HMAC verification | `auth.ts` | Auth bypass if body parser strips raw body |
| ME-4 | No auto-hide for revealed private key | `ExportPrivateKeyScreen.tsx` | Screen shoulder-surfin risk |
| ME-5 | Custom error messages in production | `errorHandler.ts` | Information disclosure |

### Low Severity
| ID | Finding | Location | Impact |
|----|---------|----------|--------|
| LO-1 | Console warnings in production | `transactions.ts`, `secureStateStorage.ts` | Information leakage in logs |
| LO-2 | test() regex without anchoring | `envValidation.ts` | False positives in environment validation |
| LO-3 | Prisma `_sum` type assertion bypass | `merchant.ts` | Potential type safety issues |

## Phase 7: Remediation Roadmap

### Immediate (Block mainnet deployment)
- [ ] Fix multi-chain address derivation (CR-1)
- [ ] Replace custom SHA-256 with audited library or use ethers.js built-in (CR-2)
- [ ] Remove clipboard copy for private key, use secure share sheet (CR-3)
- [ ] Implement real proof verification in smart contracts (CR-4)
- [ ] Move API keys to backend proxy (CR-5)

### Short-term (Before testnet launch)
- [ ] Add explicit chain ID verification before signing (HI-1)
- [ ] Implement dynamic gas estimation with congestion detection (HI-2)
- [ ] Increase speed-up multiplier or make it configurable (HI-3)
- [ ] Validate webhook URLs against allowlist (HI-4)
- [ ] Add testnet/mainnet derivation path suffix (HI-5)
- [ ] Add idempotency key to invoice creation (HI-6)

### Medium-term (Production hardening)
- [ ] Add authentication to invoice status endpoint (ME-1)
- [ ] Lower global rate limit to 300/min (ME-2)
- [ ] Ensure rawBody availability for HMAC (ME-3)
- [ ] Auto-hide private key after 30 seconds (ME-4)
- [ ] Sanitize error messages in production (ME-5)

### Ongoing
- [ ] Run `npm audit` / `pnpm audit` on all packages
- [ ] Review Dependabot alerts for ethers, react-native, expo
- [ ] Penetration testing on backend API endpoints
- [ ] Smart contract formal verification with SMT solver
- [ ] Mobile app security audit (OWASP MASVS)
