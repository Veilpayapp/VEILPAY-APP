Root-cause → fix mapping

For each problem: the exact state variable, the failing mechanism, and the surgical fix.

A  Mainnet shield failure (never reaches send)

Two distinct scenarios — do not conflate

(a1) No mainnet manifest: SPP_MAINNET null → canActivatePrivacyAsset false (privacyAssets.ts:78-81) → handleSelectPrivacyAsset toasts and returns early (HomeDashboardScreen.tsx:660-663). Never reaches the send flow.

(a2) poolOps off on a configured asset: sppNativeCapabilities().poolOps === false → latch lands unavailable (:736-741) with no outgoing edge. Send is gated on ready, so nothing that consumes unavailable blocks the dispatch — sppDeposit/Withdraw/Transfer hit the native layer and throw SPP_OPS_NOT_READY, surfacing as a failed modal.

Mechanism

On mainnet the latch often does flip ready but for the wrong reason: the quiet probe at :467-468 sets ready purely from account.aspInserted — a write that was submitted but not yet visible on-chain (the 4294967295 cursor / event-paging problem documented in sppOnboard.ts:59-120). The probe is thus a false-positive ready, gating sends that then fail in the prover. Code comment :764-766 admits exactly this.

Fix

(a1): surface the disabled reason on the shield card, don't rely on a bare toast. (a2): wire an unavailable → disabled send guard at the hook level (usePaymentTransaction.ts) so dispatch never reaches the native layer when privacyReadyStatus === 'unavailable'. Both: de-risk the probe — gate the :467-468 ready on existing.aspInserted && existing.aspMembershipContractId === cfg.aspMembershipId && existing.keysRegistered && existing.registryContractId === cfg.registryId (:751-760) instead of aspInserted alone, or make the latch go ready only through a real findAspLeafOnChain re-check (sppOnboard.ts:266).

B  Repeated re-sync on toggle + banner not clearing

Re-sync on toggle

privacyReadyStatus is sticky (:697 prev ?? setting_up), but handleSelectPrivacyAsset unconditionally re-runs the whole heavy block — ensureSppAccountReady (:818), the 3-attempt prepareSppOp poll (:778/:831) and the aspReady-branch prepareSppOp (:867) — on every enter even when setupComplete is already true. privacySetupGenRef aborts in-flight work (:667) but the next enter redoes all of it; the "alreadyRecovered → local only" short-circuit (:900-903) only suppresses the native balance open, not the probe (:447-484) or the prepare/poll. The user sees "Syncing private account…" → "Sync ready" churn per toggle.

Banner not clearing

Only two null-writes on privacyStatusDetail — enter :676, exit :967. handleRefreshPrivateBalance re-writes it on every focus (:332/:338/:354/:377) with no matching clear, so the exit-clear is undone by an async refresh that landed after it (or by the next focus bounce), re-rendering a stale "Sync ready"/error banner on the standard screen. PrivacyStatusBanner.tsx is stateless with no auto-hide timer.

Fix

Re-sync: in handleSelectPrivacyAsset, short-circuit the heavy block when setupComplete is already true and status is already ready (skip ensureSppAccountReady + the poll; jump straight to a light refreshPrivateBalanceSmart). Banner: (1) add an expiry timer in PrivacyStatusBanner.tsx for ready/info variants (~3s auto-hide); (2) gate privacyStatusDetail writes in refreshPrivateBalanceSmart's non-user paths on a fresh setupGen === privacySetupGenRef.current, and let the probe (:447) setPrivacyStatusDetail(null) when the mode flipped off.

C  Prove freeze + loading-animation centering

Prove freeze

setTxStatus('proving') (:1102) has no timeout. The proving → terminal edge depends solely on await sppDeposit/Withdraw/Transfer (:1115-1124) settling. When the native prover hangs, proving is absorbing — nothing escapes it. Unlike the standard path's pollAbortRef (:210/:1217), the SPP path has no AbortController. The unmount guard !isMountedRef.current (:1150) returns before any setTxStatus, so leaving the screen mid-prove leaves status stuck.

Loading centering

Because no terminal failed/confirmed ever fires, the TransactionStatusCard modal never flips from its in-progress geometry to the result geometry — the loading indicator stays in the wrong (un-finalized) layout and the spinner sits off-center.

Fix

Wrap the SPP prove in a watchdog: Promise.race around :1112-1124 with a ~30–45s budget (mirroring the ~10–20s promise) ending in setTxStatus('failed') + setTxResult({hash:'',status:'failed',error:'Proof generation timed out'}). In the !isMountedRef.current branch (:1150), set failed instead of a bare return, and thread an AbortController on the private path so the prover can be cancelled.
